# 취약점의 다중 트래픽 증거

**언어:** [简体中文](../漏洞流量证据.md) | 한국어

취약점 상세의 "연결된 트래픽"은 여러 페이지에 걸친 다중 선택, 용도와 설명, 순서 변경 및 연결 해제를 지원합니다. 트래픽 페이지에서도 여러 기록을 선택하여 기존 취약점 하나에 한 번에 연결할 수 있습니다. 작업이 상속한 취약점 증거는 읽기 전용이며, 수정하려면 원본 작업으로 이동해야 합니다.

시스템 설정의 "Agent 자동 트래픽 연결"은 기본적으로 꺼져 있습니다. 조회 및 수정은 `/api/settings`의 `agent_traffic_binding`을 사용합니다. 켜면 요청/응답 조회, 도구 호출 및 프롬프트에 따른 Token 사용량이 늘어나며, 다음 Agent 라운드부터 새 설정을 사용합니다. 끄면 자동 연결 매개변수와 추가 연결 도구를 숨기고 자동 연결 지침을 주입하지 않으며, 이미 실행 중인 세션이 새로 제출하는 자동 연결도 거부합니다. 수동 연결, 트래픽 캡처, 저장된 증거의 조회 및 내보내기는 영향을 받지 않습니다.

켜면 기본 흐름은 "발견 항목 저장 → 보고서 Agent 자동 시작 → 트래픽 확인 및 연결 → 최신 증거 버전으로 보고서 작성"입니다. 보고자는 `evidence`에 검증 명령, 주요 출력, 이미 존재하는 실제 트래픽 ID 및 용도를 남깁니다. 보고서 Agent는 취약점 상세와 실행 기록을 참고하여 `traffic_search` / `traffic_get`으로 확인한 뒤 `bind_finding_traffic`을 호출하고, 최신 `version`을 읽어 보고서를 저장합니다. 스위치를 끄면 보고서 Agent에 원시 트래픽 검색/조회 도구를 추가로 제공하지 않으며 자동 연결도 하지 않습니다. 수동으로 연결한 스냅샷을 읽고 보고서를 생성하는 것은 계속 가능합니다.

기존 호출자와 호환됩니다. `report_finding`의 `traffic_refs` / `evidence_hint_id`로 여전히 명시적인 즉시 연결을 할 수 있습니다. 연결은 선택 사항입니다. TCP 등 비 HTTP 취약점이거나, 수집하지 않았거나, 정확한 기록을 찾지 못한 경우에는 참조를 생략해도 정상적으로 보고하고 보고서를 작성할 수 있습니다. 명령 출력, 로그 등 다른 검증 가능한 증거를 남기고 연결하지 않은 이유를 설명하는 것이 좋습니다. 새 필수 필드는 추가하지 않습니다. 제출한 ID는 모두 유효하고 본문이 완전해야 합니다. 하나라도 실패하면 이번 연결 작업 전체를 롤백합니다. 보고와 함께 명시적으로 연결할 때 연결이 실패하면 보고 전체를 롤백합니다. 같은 스냅샷을 반복 추가해도 연결이 늘어나거나 설명을 덮어쓰지 않습니다.

## Agent ID와 보고서 버전

`report_finding`에 선택 매개변수가 추가되었습니다. 배열 순서가 초기 증거 순서입니다.

```json
{
  "traffic_refs": [
    {"traffic_id": "真实流量ID", "role": "baseline", "note": "正常账户请求"},
    {"traffic_id": "另一个真实流量ID", "role": "proof", "note": "复现请求"}
  ]
}
```

용도는 `baseline`(정상 대조), `proof`(취약점 증명), `verification`(추가 검증), `supporting`(보조 증거, 기본값)입니다. 먼저 `traffic_search` / `traffic_get`으로 실제 기록을 확인하세요. 도메인과 시간은 후보를 추리는 데만 사용하며 작업 귀속을 추정하지 않습니다.

프롬프트는 [CyberStrikeAI의 취약점 보고 도구 지침](https://github.com/RuoJi6/CyberStrikeAI/blob/54d56774b8bd285817d16d48b70a4a5e6e0963f7/internal/app/vulnerability_tools.go)을 참고하며, 이 프로젝트의 선택적 연결 계약을 함께 적용합니다. 트래픽 패키지가 없는 이유를 필수로 검사하지 않습니다. ID를 추측해서는 안 되며, 패키지를 보충하기 위해서만 같은 탐지를 반복해서도 안 됩니다.

반환값의 첫 줄은 여전히 `finding recorded: <探索节点 ID>`입니다. 그 뒤의 JSON은 독립 취약점 기록의 `finding_id`, 탐색 노드의 `finding_node_id` 및 연결 요약을 제공합니다.

- `get_finding_traffic(finding_id)`는 **독립 취약점 기록 ID**를 사용하며, 정렬된 목록과 `version`을 반환합니다. `binding_id`, `side=request|response`, `offset`, `length`를 전달하면 본문을 구간별로 읽을 수 있으며, 각 구간은 최대 8192바이트입니다.
- `update_finding_report`의 `finding_id`는 **계속 탐색 노드 ID를 사용합니다.** 새로 추가된 `evidence_version`에는 실제로 읽은 버전을 넣습니다. 생성 중 증거가 바뀌면 이전 버전의 쓰기를 거부하므로 다시 읽고 생성해야 합니다.
- 기존 보고서 호출에서 버전을 전달하지 않으면 기존 트래픽 증거를 반영했다고 주장하지 않습니다. 연결, 설명, 용도 또는 순서가 바뀌면 기존 보고서에 업데이트가 필요하다고 표시합니다.

자동 연결을 켜면 `add_hint` / `add_task_hint`는 단일 힌트 또는 일괄 `hints`의 각 요소에 `traffic_refs`를 저장할 수 있습니다. Planner가 대신 보고할 때 `evidence_hint_id`를 전달하여 이 작업의 해당 힌트에 있는 참조를 명시적으로 선택할 수 있습니다. 상속된 힌트를 참조할 수는 없습니다. 시스템은 도메인, 시간 또는 조회 기록으로 연결을 추측하지 않습니다. 제출이 실패하면 취약점 일부만 생성하거나 보고서를 미리 시작하지 않습니다.

기존 취약점에 연결이 빠졌다면 `bind_finding_traffic(finding_id, traffic_refs)`로 추가 연결할 수 있으며 다시 등록할 필요는 없습니다. `list_findings` / `list_task_findings` / `node_detail` / `get_task_node_detail`은 명확한 `finding_id`와 `finding_node_id`를 반환합니다. 기존 `id`는 탐색 노드 의미를 유지합니다.

시작 시 기존 도구 schema에는 선택 속성만 추가합니다. 원래의 기본 트래픽 도구 연결 대상을 보고서 Agent까지 확장하고, 추가 연결 도구는 기본적으로 보고서 Agent에 제공합니다. 사용자 지정 연결 목록, 프롬프트, 설명 및 활성화 상태는 보존합니다. 지침은 최종 도구 조립 후 일괄 추가합니다. 보고 역할은 기존 증거를 인계하고, 보고서 Agent는 확인, 연결 및 보고서 작성을 담당합니다. 플랫폼 대화에 작업 컨텍스트가 없으면 구조화된 힌트로 작업 Agent에 인계해야 하며 직접 보고하지 않습니다. 작업 완료를 판단하기 전에 기존 증거를 먼저 인계해야 하지만, 트래픽 패키지가 없다고 강제로 기다리지는 않습니다. 실패한 `report_finding`은 보고서 Agent를 시작하지 않습니다.

## API

기본 경로는 `/api/exploration/findings/{finding_id}/traffic`이며, 독립 취약점 ID를 사용합니다. 기존 인증을 사용하며, `context_task`로 작업 가시성과 상속된 증거의 읽기 전용 여부를 검사합니다.

| 메서드 / 상대 경로 | 요청 / 반환값 |
| --- | --- |
| `GET` | 정렬된 요약, 증거 버전, 보고서가 사용한 버전 |
| `POST` | `{"traffic_refs":[...]}` 전체 일괄 추가 |
| `PATCH /{binding_id}` | `{"version":1,"role":"proof","note":"说明"}` |
| `DELETE /{binding_id}` | `{"version":1}` |
| `PUT /order` | `{"version":1,"binding_ids":["2","1"]}`, 반드시 전체 목록이어야 함 |
| `GET /{binding_id}` | 스냅샷 메타데이터와 범위가 제한된 본문 미리보기 |
| `GET /{binding_id}/body` | `side`, `offset`, `length`. `download=1`로 전체 원본 바이트 다운로드 |

버전/정렬 대상 집합 충돌 또는 아카이브 중 쓰기는 `409`, 상속된 증거 쓰기는 `403`, 존재하지 않거나 해당 취약점에 속하지 않은 연결은 `404`를 반환합니다. 트래픽/첨부 파일 읽기 및 검증 실패는 명시적인 오류를 반환합니다.

## 저장 및 마이그레이션

시작 시 PostgreSQL에 멱등 마이그레이션을 적용합니다. `traffic_evidence_snapshots`, `finding_traffic_bindings`와 `findings.evidence_version` / `report_evidence_version`(기본값 0)을 추가합니다. 과거 텍스트를 근거로 추측하여 연결을 보충하지 않습니다.

스냅샷에는 원본 트래픽 ID, 수집 시각, URL, 메서드, 상태, 요청/응답 헤더, 본문 길이 및 SHA-256을 저장합니다. 본문은 해시에 따라 `<data>/evidence/blobs/<前两位>/<hash>.bin`에 저장합니다. 정리할 수 있는 `data/traffic`과 별개이며, 여러 취약점이 스냅샷/본문을 공유할 수 있습니다. 스냅샷은 내용 업데이트 인터페이스를 제공하지 않으며, 검증 결과가 일치하지 않으면 읽기와 내보내기가 실패합니다.

원본 트래픽의 쓰기 잠금 아래에서 전체 본문을 읽습니다. 큰 본문의 blob과 기존 디렉터리 기록도 포함합니다. 먼저 파일을 영속화하고 검증한 뒤, 단일 PostgreSQL 트랜잭션으로 탐색 노드, 의도 관계, 취약점, 스냅샷 및 연결을 저장합니다. 커밋 후에만 planner에 알립니다. 실패하면 참조되지 않는 파일이 남을 수 있지만 일부 업무 기록만 생성되지는 않습니다.

PostgreSQL advisory lock `7337741004`로 증거 파일과 SQL 참조를 조율합니다. 작업 행 잠금은 아카이브가 대기열에 들어간 후의 증거 수정을 금지합니다. 복구 시 본문 설치부터 메타데이터 커밋까지 전체 과정에서 증거 잠금을 유지합니다. 취약점을 삭제하면 연결도 연쇄 삭제합니다.

정리기는 매시간 실행하며 참조가 없고 진행 중인 작업에도 속하지 않은 내용만 최소 24시간의 유예 후 회수합니다. 일반 트래픽 정리는 증거 디렉터리를 건드리지 않습니다. 활성 데이터를 백업할 때는 PostgreSQL과 `data/evidence`를 함께 백업하세요.

## 내보내기 및 아카이브

Markdown에는 정렬된 증거 목록과 버전이 포함되고, JSON에는 메타데이터가 포함되며, CSV에는 개수와 연결 ID가 추가됩니다. `md-zip`은 취약점 Markdown을 보존하며 다음 파일을 제공합니다.

```text
evidence/<finding_id>/<binding_id>/
  manifest.json
  request.http
  response.http
  request.bin
  response.bin
```

Markdown은 상대 링크로 요청/응답 메시지를 참조합니다. 다운로드를 보내기 전에 첨부 파일 복사, 해시 검증, 압축, 디스크 동기화 및 모든 ZIP 항목의 CRC 읽기 검증을 완료합니다. 파일이 없거나 손상되면 다운로드 전체가 실패합니다. 전체 첨부 파일은 원본 바이너리 바이트를 보존합니다.

아카이브 v3는 취약점 연결 관계에 따라 스냅샷과 본문을 수집하며 원본 트래픽이나 도메인에 의존하지 않습니다. 패키지 검증을 완료한 뒤에만 활성 데이터를 정리하며, 공유 증거는 계속 보존합니다. 복구 시 먼저 본문을 검증하여 설치하고, 그다음 트랜잭션으로 메타데이터와 연결을 복구합니다. 실패 후 재시도를 지원합니다. v1/v2도 계속 복구할 수 있으며, 없는 새 필드는 명시적으로 0으로 채웁니다.

## 검증 및 경계

각 테스트 패키지에는 독립적으로 새로 만든 PostgreSQL 테스트 데이터베이스를 사용하고 `ARTEX_PG_DSN`으로 지정하세요. 남은 작업/모델 픽스처가 백그라운드 실행을 트리거하지 않게 하기 위함입니다. 관련 패키지의 전체 테스트를 실행하고 설정 누락으로 건너뛴 테스트가 없는지 확인하세요.

```sh
# 每个包运行前将 ARTEX_PG_DSN 设为对应的独立测试库；显式配置失败必须报错。
go test ./<package> -count=1
go test -race -p 1 ./evidence ./db ./agent ./server -run 'TestEvidence|TestFindingTraffic|TestFindingEvidence|TestReportFindingAtomicContract|TestTaskArchive'
```

프런트엔드 검증에는 `npx tsc --noEmit`, 영향을 받는 파일의 Biome 검사, Webpack 빌드 및 `NEXT_EXPORT=1` 정적 내보내기가 포함됩니다. 실행 중인 개발 서비스를 덮어쓰지 않도록 별도의 캐시 디렉터리를 사용하세요.

로컬 엔드투엔드 검증은 별도의 포트, 통제된 HTTP / 도메인 HTTPS 대상 및 임시 데이터 디렉터리를 사용합니다. 두 연결 진입점, 페이지 간 선택, 순서/설명, 오류 메시지, 상속된 증거의 읽기 전용 동작, 다운로드를 검증합니다. 또한 원본 트래픽을 삭제한 후 내보내기, 아카이브, 활성 본문 회수, 복구 및 해시 검증도 다룹니다.

첫 버전은 전역 증거 조정 잠금을 사용합니다. 대량 연결/내보내기 또는 느린 첨부 파일 다운로드 중에는 다른 증거 작업이 기다릴 수 있습니다. 기록된 트래픽이나 완전한 본문이 없으면 증거를 만들어 보충할 수 없습니다. 이 기능은 캡처 스위치를 바꾸지 않으며 HTTPS로 IP에 직접 접근할 때의 인증서 문제도 처리하지 않습니다.
